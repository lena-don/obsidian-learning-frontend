**API** (Application Programming Interface программный интерфейс приложения) — это ==набор правил и готовых команд, с помощью которых разные программы могут общаться и обмениваться данными друг с другом==.
[Подробнее об API на Яндекс Практикуме](https://practicum.yandex.ru/blog/chto-takoe-api/)

**REST** (Representational State Transfer передача состояния представления) — ==это набор правил для того, как сайты и приложения общаются друг с другом через интернет. ==

**REST API** (Representational State Transfer Application Programming Interface) — это [архитектурный стиль] ==взаимодействия между приложениями, который позволяет клиенту и серверу обмениваться данными через стандартные запросы по протоколу HTTP==. 
[Подробнее о REST API на Яндекс Практикуме](https://practicum.yandex.ru/blog/chto-takoe-rest-api-i-kak-rabotaet)

#### Как это работает
- **Клиент** (например, браузер или мобильное приложение) отправляет запрос на сервер.
- **Сервер** обрабатывает запрос и возвращает ответ, чаще всего в формате JSON.
- Каждый объект или набор данных на сервере имеет свой уникальный адрес — **URI** 

#### Основные методы HTTP
Для управления данными используются стандартные команды (соответствуют операциям CRUD —  базовым функциям работы с данными: Create, Read, Update, Delete): 
- **GET** — получить данные или список объектов.
- **POST** — создать новый объект.
- **PUT** или **PATCH** — обновить существующий объект.
- **DELETE** — удалить объект.


## Главные принципы [REST](https://ru.wikipedia.org/wiki/REST) 
— это шесть архитектурных ограничений, которые определяют, как клиент и сервер обмениваются данными.

Пять принципов являются обязательными, а один — опциональным. 
#### 1. Клиент-серверная модель (Client-Server)
- **Суть:** Интерфейс пользователя (клиент) и хранение данных (сервер) полностью разделены.
- **Польза:** Клиент не думает о том, как хранятся данные, а сервер не зависит от того, как выглядит экран у пользователя. Они развиваются отдельно.

#### 2. Отсутствие состояния (Stateless)
- **Суть:** Сервер не хранит информацию о предыдущих запросах клиента.
- **Польза:** Каждый запрос должен содержать все данные, чтобы сервер понял его без подсказок. Это повышает надежность системы.

#### 3. Кэширование (Cacheable)
- **Суть:** Ответы сервера могут быть помечены как кэшируемые (или нет).
- **Польза:** Клиент или промежуточный сервер может сохранять ответ и использовать его повторно, не нагружая основной сервер. Это ускоряет работу.

#### 4. Единообразие интерфейса (Uniform Interface)
- **Суть:** Правила обращения с данными одинаковы для всех. Ресурсы имеют уникальные адреса (URL), а для работы с ними используют стандартные методы (обычно из протокола HTTP: `GET`, `POST`, `PUT`, `DELETE`).
- **Польза:** Код становится понятным, а разные системы легко интегрируются друг с другом.

#### 5. Многоуровневая система (Layered System)
- **Суть:** Клиент может общаться не напрямую с сервером, а через промежуточные узлы (балансировщики, прокси, системы безопасности).
- **Польза:** Клиент об этом не знает и думает, что работает с конечным сервером. Это помогает масштабировать систему.

#### 6. Код по требованию (Code on Demand) — _необязательный принцип_
- **Суть:** Сервер может передать клиенту исполняемый код (например, скрипт на JavaScript), который клиент сразу выполнит.
